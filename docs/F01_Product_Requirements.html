0. 执行摘要与决策状态

产品定义。 IDP API Fabric 是面向 IDP 多供应链产品的统一 API 契约、资产目录、治理与开发者体验平台。它为 CargoPai、IDP Parcel、IDP Brant、IDP Prism 等产品提供共享的标准和治理能力，并保持各产品 API 契约、数据与授权、发布生命周期和对外品牌体验的独立性。

核心原则。 One Platform · Multiple Products · Independent Contracts。平台统一治理与工具链，产品保有业务边界。API Fabric 不是 API Gateway、身份提供方、消息代理，也不拥有业务订单、运单、报价或库存的权威数据。

双门户。 内部 IDP Engineering Portal 是 API 工程治理工作台；外部 Product Developer Portal 是按产品品牌隔离的开发者文档与自助集成入口。两个门户逻辑分离，可共享基础设施与组件，但不能共用无差别的授权访问面。

交付方向。 以契约注册→验证→审核→不可变发布→受控门户展示→必要时撤销/恢复构成最小可用闭环；以 CargoPai 为首个试点，随后复用至其他产品。真正的沙箱首次调用、完整企业级自助集成、运行时一致性、高级治理和 AI 工具治理分阶段交付。MVP 的文档阅读闭环不是 BG-03 所述的真实沙箱接入成功。

1. 背景、问题定义与产品机会

1.1 业务背景

IDP 供应链产品覆盖国际货运代理、跨境小包、国际贸易及仓储物流。不同产品拥有独立的 DDD 限界上下文、API 版本、合作伙伴和业务对象，但在 API 文档生产、代码示例、治理策略、版本管理、安全验证与开发者接入方面存在高度共性。

1.2 现状风险（待调研证实，不作为已发生事实）

  • 文档可能以 Swagger / OpenAPI 输出为主，缺少可操作的业务集成流程和开发者接入说明。
  • API 定义与实际代码可能分离，接口发布与文档发布无法形成可追溯闭环。
  • 不同产品可能重复建设文档站点、校验规则和开发者管理功能。
  • 内部 / 外部 API 曝光边界不清时，存在跨产品可见性和敏感信息泄露风险。
  • 异步事件、Webhook、SDK 与 REST API 的契约治理可能由不同流程管理，难以判断兼容性。

这些是启动需求访谈时应验证的 问题假设，不能写成已审计确认的现状。

1.3 产品机会

建设统一平台，把 API 从“附属文档”升级成可发现、可验证、可审批、可发布、可持续维护的工程资产；通过双门户降低内部协作成本和外部集成摩擦，同时保持产品自治与数据安全。

2. 产品愿景、目标与非目标

2.1 愿景

使每个已发布的产品 API 都拥有明确契约、责任人、可见范围、兼容性政策、发布证据和可供开发者完成实际业务的使用说明。

2.2 业务目标（BG）

编号 目标 可观察的结果 验证方式
BG-01 降低 API 治理重复建设 新产品不需重新搭建独立的基础文档与校验平台 接入过程成本和功能复用清单
BG-02 提升接口发布可靠性 发布前有契约校验、兼容性判断、授权审查和审计记录 发布审计与质量门禁结果
BG-03 降低外部接入摩擦（V1 达成） 外部开发者可从文档发现完成可验证的真实沙箱首调；MVP 只证明安全可读的文档发现闭环 开发者任务走查、授权记录和实际沙箱调用证据
BG-04 维护跨产品自治 一个产品的变更不意外影响另一产品的私有契约与访问范围 权限、发布和多产品隔离测试
BG-05 实现契约可追溯 可从门户文档追踪到具体发布制品和源修订 发布制品摘要与来源链路
BG-06 支持未来 AI-Native 集成 合规输出可供 Agent 消费的受控工具元数据 V2 验收，V1 预留接口边界

2.3 非目标（明确排除）

  1. 不替代产品自身的 API 实现和领域逻辑，不直接成为订单、运单、库存、报价的数据中心。
  2. 不自建通用 API Gateway 的全量流量转发、WAF、负载均衡和限流执行功能；通过适配器集成现有基础设施。
  3. 不自建完整 IAM / OAuth 2.0 / OIDC 身份提供方，原则上对接已有身份服务；应用注册与权限业务流程可由 Fabric 承担。
  4. 不替代 Git 仓库管理、CI/CD 执行器、消息代理或事件流引擎。
  5. 不强制所有产品共享一个 OpenAPI 文件、业务实体、发布节奏或数据表。
  6. 不在 MVP 内实施完整计费结算、API 商业化市场、通用低代码集成平台或自治 Agent Runtime。
  7. 不因生成 API 文档而自动授权任何接口；文档转换不构成运行时安全控制。

2.4 业务成功指标及基线采集

指标 定义与计算 基线与目标处理 数据来源

2.5 Build vs Buy 与经济性边界

Fabric 的差异化部分应集中在 多产品自治、契约治理策略、DDD 资产关系、双门户集成体验与可追溯发布流程。OpenAPI 解析、Lint、兼容性分析、文档渲染、OAuth 身份服务和 API Gateway 等成熟技术不应因“自建平台”定位而全部重写。

能力类别 优先策略 评估维度 交付依据
契约与治理核心业务 优先自研领域编排，复用成熟底层库 数据权威、规则自治、可替换性、测试可控 F02/F03/F04
OpenAPI/AsyncAPI 解析和差异工具 优先选用标准兼容的组件 规范覆盖、质量、许可、维护、Go 兼容 F04/F07
开发者文档渲染 优先集成成熟组件 无障碍、多品牌、性能、安全、可定制性 F06/F07
IAM、Gateway、CI/CD 优先适配现有可信基础设施 权责、安全域、SLA、运维与供应商锁定 F02/F05

必须在 F02/F08 比较至少两类可落地方案的 一次性开发成本、年度运行成本、迁移成本、维护负担和退出策略；本稿没有足够样本，不给出未经验证的成本节约百分比。

3.2 概念区别（后续由 F03 精确建模）

3.3 逻辑隔离规则

  • 产品、Workspace、租户、组织、外部应用和环境是不同维度，权限判断必须显式求交，而非互相替代。
  • API 资产、搜索索引、文档发布物和审计记录都必须包含可验证的可见范围或访问策略。
  • 可公开产品文档与需要认证的私有 API 文档必须分开设计；访问文档的权限与执行 API 的权限是不同授权。
  • 外部产品的品牌、域名和发布范围独立；复用底层渲染引擎不意味着共享用户会话或敏感资料。
  • 部署隔离级别（共享实例 / 独立命名空间 / 独立实例）由 F02 与 F05 基于风险和规模决定。

5. 端到端业务旅程与用例

用例 参与者 主要流程 关键失败/例外处理
UC-01 产品接入 平台管理员、产品负责人 注册 Product → 建立 Workspace → 确认归属与策略 → 接入源仓库 产品标识冲突、权限不完整时拒绝激活

7.1 MVP 最小纵向切片

9. 业务规则与状态语义（产品层约束）

  1. 契约修订不等于发布版本。 同一 Asset 可关联多个 Revision、Release 和 Publication。
  2. Release 不可变。 修改内容必须生成新 Release，不能覆盖旧正式制品。
  3. 发布对象明确。 发布必须声明目标产品、环境、受众与门户，不允许依赖含糊的全局 public=true。
  4. 权限最小化。 拥有查看契约权限 ≠ 拥有调用生产 API 权限；拥有内部门户权限 ≠ 可访问所有产品。
  5. 审批与运行事实分离。 审核通过并不能证明生产运行接口一致，漂移检查是独立证据。
  6. 检查结果可解释。 兼容性判断必须记录比对基线、规则版本和可追踪证据。
  7. 重试可恢复。 导入、审核、发布等长操作应有显式状态，重复触发不应产生不可控副作用。
  8. 事件与请求响应不同。 异步事件必须另定义语义、顺序与幂等消费指南，不能仅复用 OpenAPI 描述。
  9. 产品自治。 平台规则可以约束最低安全基线，但不能将 Parcel、CargoPai 的 Shipment 强行合并为一个领域聚合。
  10. AI 工具严格受控。 生成 MCP 工具描述不构成执行授权；写操作和敏感业务操作须经独立决策。
