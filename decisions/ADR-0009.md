## 问题

### 网关期待 Fabric 做什么

- **批准在 Fabric，配置和观察在网关。** 网关 ADR-0006（Accepted）的推荐决策是“Fabric 管 APIAsset、Release、PublicationSlot 及审批；Gateway 管原生代理配置和实际 Observed State；经版本化意图和受控适配器协作”。同篇列出的替代方案是 Fabric 直接写网关数据库或在业务请求路径中做代理，没有采用。两边各有自己的存储，靠幂等、CAS、Outbox 和回滚达到最终一致（同篇“成本与剩余风险”）。
- **网关一侧已经做好。** 网关 ADR-0020（Accepted，2026-11-24）新增 `cmd/gateway-fabric`，按网关 `contracts/fabric/route-publication-intent.openapi.yaml` 收 `POST /v1/route-intents` 和 `GET /v1/route-intents/{intent_id}/status`。回环套件 `tests/integration/fabric/` 连跑两遍，9 个用例、90/90 项检查；套件里“Fabric 一侧是替身客户端”（同篇“做出来了（V1.0）”）。网关开发计划 §6 写着这项对接“要等……Fabric 一侧”。网关 `README.md` 目录表 `cmd/gateway-control` 一行的末句是“发布的批准还没有”。
- **网关所有者的阶段 0 范围**：“新路由与认证方案声明走 API Fabric，应急处置留在现有回环 `gateway-console`”（网关 ADR-0020 抬头）。
- **网关对 Fabric 文档提的定点变更**（网关 `docs/integrations/Fabric_and_Gatekeeper_Change_Impact.md` §API Fabric，状态 Proposal，没有改 Fabric 文档）：F01 补充消费者 API 对应的出站路由绑定与发布意图，不把第三方提供方契约包装为我方自有 API；F03 区分 Fabric 的 `PublicationSlot` 与网关的 `RouteBinding`，用稳定 ID 引用，禁止跨数据库共享写主；F04 为提供方契约定义认证方案元数据、变更影响及验证方式，秘密永不进入契约；F05 消费者 API 不自动对外公开；F07/F08 不把文档发布视为网关 `ACTIVE`。同一文件末条：跨系统的模型和流程变更要目标系统 Owner 明确接收。
- **接口要点**：信封是 `idempotency_key`、`release_ref`、`target_id` 加一条 RouteIntent；mTLS，只认一个客户端身份；同步校验失败 422，幂等冲突和代次冲突 409，受理 202、`state` 为 `DRAFT`；状态只用契约 `ReleaseState` 的 16 个词；回读摘要相等才是 `ACTIVE`（网关 ADR-0020 推荐决策 2、3、6）。下面各条逐项引用。

### Fabric 现在有什么

- **没有“消费者 API”。** `APIAsset` 是“产品内有稳定身份的 HTTP / Event API 资产”（F03 §2），`api_kind` 只有 `HTTP`、`EVENT`（`api/openapi.yaml` 的 `AssetKind`）。FR-004 的 Consumer Application 是外部开发者登记的客户端应用，与网关说的消费者 API（IDP 工作负载经出站网关调用的第三方 API）不是一回事。
- **发布目标只有门户。** `PublicationTarget = Product × Audience × Environment × Portal`（F03 §2、ADR-0004），登记要 `audience_config_id` 和 `portal_key`；受众是 `public`、`partner`、`internal`，环境是 `sandbox`、`production`；目前只有 `internal` 受众的目标能激活，槽位的 `delivery_status` 恒为 `UNKNOWN`（F04 §11.6）。
- **Release 依据检查，没有批准。** 准备 Release 以检查为准，豁免在准备时逐条填写（CR-0001 决定 1、2）；同一个人可以导入、检查、准备 Release 并发布（决定 3）；策略更新后已有 Release 仍可发布和恢复（决定 5）。
- **网关只出现在边界和 V1 需求里。** Fabric 不自建网关的流量转发（F01 非目标 2），文档不授权任何接口（非目标 7）；网关适配器“只提供部署快照或经批准的配置意图”，连接失败显示 `UNKNOWN/STALE/FAILED`（F02 §12.3）。漂移识别 FR-039、连接状态 FR-045、网关元数据适配接口 FR-060 都是 V1。IAM 与网关的真实接入是 F01 DEC-06 和 F08 OD-08-04，都没有定。
- **出站投递只有 Outbox。** `fabric-worker` 把 Outbox 事件以 Bento 信封 POST 给一个接收端，可带 Bearer，退避 1 秒到 5 分钟，12 次后记为 `ABANDONED`（`cmd/fabric-worker/README.md`）。没有 mTLS 客户端，也没有工作负载证书。

### 要回答的

一个 Fabric Release 怎样变成网关能收的发布意图；网关说的“Fabric 批准”在 CR-0001 之后是什么；Fabric 的目标和槽位与网关的路由绑定是什么关系；Fabric 以什么身份提交、怎样重试；状态怎样读回来而不误报；撤回、回退和阻断在网关那边意味着什么。

## 候选决策

### 1. 消费者 API 是资产的一种来源，不是新的接口类型

- `APIAsset` 增加登记后不可改的 `origin`：`IDP_OWNED`（默认，现有资产都是）或 `EXTERNAL_PROVIDER`。`EXTERNAL_PROVIDER` 的资产必须带 `provider_id`，格式与网关的 `provider_id` 相同，`^[a-z][a-z0-9-]{1,63}$`（网关 `contracts/gateway/route-intent.schema.json`）。`api_kind` 仍只表示协议。
- 统一语言里叫“外部提供方 API”（`ExternalProviderAPI`），不叫 Consumer Application，也不简称 Consumer，避免与 FR-004 撞名。
- 契约写的是 IDP 工作负载经出站网关看到的样子：路径在 `/providers/{provider_id}/` 下，即网关 G03 §0 的逻辑入口；每个要路由的操作，`operationId` 就是网关的 `operation_id`（格式 `^[a-z][a-z0-9_.-]{2,127}$`）。提供方自己的文档只作来源引用，不作为我方 API 发布。这与网关 G03 §1 一致：`ApiOperation` 的权威是“Fabric Consumer API Catalog”，“第三方接口契约不由我们伪造为权威”。
- 这类资产不能发布到 `partner`、`public` 受众的门户目标（`ASSET_ORIGIN_MISMATCH`），只能发布到 `internal` 门户目标（读文档）和第 3 条的网关路由目标（发路由）。外部开发者门户不列出它们（网关变更清单 F05）。
- 建议单设一个 Fabric 产品（例如 `idp-egress`）持有全部外部提供方 API 和网关路由目标，每家提供方一个 Workspace。出站池是按流量类和环境分的平台资源（网关 G02 §5），不属于 CargoPai 等某一个业务产品。CR-0003 决定 3 已按此决定，以接下为前提。

### 2. 认证方案只写元数据，不写秘密

- `components.securitySchemes` 描述的是契约的读者（调用出站网关的 IDP 工作负载）要出示什么，按 F04 §3.1 它不是运行时授权。提供方要什么凭证另写在文档级扩展 `x-idp-provider-auth`，按 F04 §3.2 登记进扩展注册表，只有这几个键：
  - `auth_scheme`：网关 `contracts/gateway/policies/credential-binding.schema.json` 的五个值之一；万邦、顺丰这种命名适配器用什么词，待对齐（问题 14）；
  - `credential_in`、`credential_name`：凭证放在请求头还是查询参数、叫什么，对应网关 ADR-0020 推荐决策 5 表里的放置方式；
  - 可选的 `scheme_prefix`（例如万邦的方案词）和 `oauth2_scopes`。

  不出现令牌、密钥、证书正文，也不出现账户和租户。哪个账户用哪份凭证归 Gatekeeper（网关 G02 GW-INV-01）。
- 新增四条检查规则，编号由 F04 负责人分配：要路由的操作 `operationId` 符合网关格式；路径在 `/providers/{provider_id}/` 下；`x-idp-provider-auth` 只含登记的键、`auth_scheme` 在允许值里；文档任何位置都没有网关拒收的九个敏感键的真值（`password`、`client_secret`、`secret_value`、`api_key`、`access_token`、`refresh_token`、`private_key`、`authorization`、`bearer_token`，网关 ADR-0020 推荐决策 3）。凭证形式的内容仍由 F04-GOV-004 扫描。`x-idp-provider-auth` 在两个修订之间变化时，兼容性判为 `RISKY`：网关那边要换绑定。
- 加规则会换策略摘要。已有 Release 照常发布和恢复（CR-0001 决定 5），准备新 Release 要在新策略下重新检查。
- 这份声明目前网关核不到：RouteIntent 没有 `auth_scheme`（网关 ADR-0020 背景末段），绑定来自 `gateway-fabric` 的 `--bindings` 文件（推荐决策 5）。一期它是文档和变更影响的依据；能否参与网关的核对，见问题 14。

### 3. 网关路由目标：发布目标的第二种；槽位照旧，路由绑定归网关

- 发布目标分两种：`PORTAL`（现有）和 `GATEWAY_ROUTE`。网关路由目标属于一个产品，登记时给出：
  - `gateway_key`：部署配置里登记的一个网关端点的名字。网址、服务端证书名和信任的 CA 只在部署配置里，库里不存网址，产品负责人不能把 Fabric 指向任意主机；
  - `gateway_target_ref`：作为信封 `target_id` 送出的值，`fabric-target:{publication_target_id}`；网关在 `gateway-fabric --target-id` 照填（问题 10）；
  - `gateway_pool`、`gateway_environment`（`DEV`、`TEST`、`PROD`）、`provider_id`、`credential_binding_ref`，以及上游声明 `upstream_hostname`、`upstream_port`、`upstream_tls`；
  - 路由表，每行是 `operation_id`、方法、`intent_id`、`logical_path`、`authz_profile`、`policy_bundle_ref`。

  除 `gateway_key` 和 `gateway_target_ref` 外，这些值抄自网关那份只读的 `--pool-base`，网关逐项核对，对不上是 422（网关 ADR-0020 推荐决策 4）。Fabric 不自己发明这些值，也不把它们当成自己的事实；网关若提供只读目录，改为读取（问题 7）。
- 一个网关路由目标对应一个 `gateway-fabric` 进程：网关一期一个进程一份 pool-base，也就是一家提供方、一种流量类（推荐决策 4）。目标的 `provider_id` 必须等于资产的 `provider_id`；`gateway_environment` 为 `PROD` 当且仅当 Fabric 的环境是 `production`。
- 槽位仍是 `Target × APIAsset`：`UNIQUE(target_id, api_asset_id)`、`expected_generation` CAS、操作历史、审计、Outbox 和访问阻断全部沿用（ADR-0004、F03 §5.10）。区别只在含义：网关路由目标上的槽位指针表示“Fabric 决定这个池上用这个 Release”，不表示路由已经生效。
- 一个槽位对应网关的多条路由绑定。网关的路由绑定是池 × 操作 × 方法，由 `intent_id` 标识（网关 G02 §3 的 `RouteBinding`；网关 ADR-0020 推荐决策 4：一条意图只许一个方法）。槽位上的一次激活按路由表展开成若干条意图（第 4 条）。两边只存对方的稳定引用：Fabric 存 `intent_id` 和网关回给的状态，网关存 `release_ref`、`target_id`、`contract_ref`、`approval_ref` 这些字符串；谁也不写对方的库（网关 G02 §3 末句；网关变更清单 F03）。
- 现有的门户目标接口和列表不变，只列 `PORTAL` 目标；网关路由目标用自己的资源路径（见“影响”）。

### 4. 一次激活展开成若干条发布意图

激活或恢复网关路由目标上的一个槽位时，Fabric 对路由表的每一行生成一份 `RoutePublicationIntent`。Release 里必须有这一行的 `operation_id` 和方法，路径必须等于这一行的 `logical_path` 或在它后面再加路径段，否则拒绝激活（`ROUTE_NOT_IN_RELEASE`）。Release 里有、路由表里没有的操作只出现在文档里，不发路由。

| 字段 | Fabric 送的值 | 来自 | 网关怎么核（出处） |
|---|---|---|---|
| `idempotency_key` | `fabric-op:{operation_id}:{行号}`，`operation_id` 是 Fabric 槽位操作的编号 | Fabric 数据 | 同键同体返回第一次的 202；同键异体 409；代次冲突不占这把键（网关 ADR-0020 推荐决策 3）。契约说它“每次发布尝试一个”，所以新操作用新键，重试用原来的键 |
| `release_ref` | `fabric-release:{release_id}` | Fabric 数据 | 原样抄回（推荐决策 2）。契约说明它“不是 Fabric 数据库的键” |
| `target_id` | 目标的 `gateway_target_ref` | Fabric 新配置 | 必须等于 `--target-id`，否则 422（推荐决策 4） |
| `intent.intent_id` | 路由表这一行的值，建议就用网关目录行里的 `intent_id`（如 `gwi-wanbexpress-whoami-get`；网关回环套件 `tests/integration/fabric/run.py` 的 `envelope` 用的就是它） | Fabric 新配置，抄自网关目录 | 格式 `^gwi-[a-z0-9-]{3,64}$`；同一目录行同时只能被一个 `intent_id` 占用（网关 `internal/fabricpub/domain/catalog.go` 的 `Merge`），所以跨 Release 必须不变 |
| `intent.gateway_pool` | 目标的 `gateway_pool` | Fabric 新配置 | 等于 `pool.name`，池名与流量类、环境一致（推荐决策 4；网关 `internal/fabricpub/domain/envelope.go` 的 `parseIntent`） |
| `intent.traffic_class` | `EGRESS` | 常量 | 一期只收出站（网关 ADR-0020“要仓库所有者定的”第 4 项） |
| `intent.environment` | 目标的 `gateway_environment` | Fabric 新配置 | 等于池的环境 |
| `intent.provider_id` | 资产的 `provider_id` | Fabric 数据 | 等于 pool-base 的提供方 |
| `intent.operation_id` | Release 里该操作的 `operationId` | Fabric 数据 | 与方法一起对上目录的一行，否则 422 |
| `intent.allowed_methods` | 该操作的那一个方法 | Fabric 数据 | 多于一个 422 |
| `intent.logical_path` | 路由表这一行 | Fabric 新配置，抄自目录 | 等于目录行。目录行另有 `path_match_mode`，例如万邦 `parcels.get` 是 `one_segment`（网关 `deploy/providers/wanbexpress/compile-spec.json`），所以它不一定等于 OpenAPI 路径 |
| `intent.upstream_hostname`、`upstream_port` | 目标的上游声明 | Fabric 新配置，抄自 pool-base | 等于提供方；顺丰这种内部签名器另接受 `rewrite_authority`（`catalog.go` 的 `upstreamHost`） |
| `intent.upstream_tls` | 目标的上游声明 | Fabric 新配置 | 等于目录行；`PROD` 不接受明文沙箱例外（`parseIntent`）。模式与实现不一致，见问题 6 |
| `intent.upstream_sni` | 与 `upstream_hostname` 相同，或不写 | 派生 | 写了就必须相等（`parseIntent`） |
| `intent.redirect_policy`、`provider_account_strategy`、`transport` | `DENY`、`GATEKEEPER_DECISION_BINDING`、`HTTP` | 常量 | 模式的出站分支要求前两个；实现另要求 `transport` 是 `HTTP`（问题 6） |
| `intent.credential_binding_ref` | 目标的值，`gatekeeper:` 开头 | Fabric 新配置，由网关和 Gatekeeper 给出 | 等于 pool-base 提供方的值，并且在 `--bindings` 里（推荐决策 5） |
| `intent.authz_profile`、`policy_bundle_ref` | 路由表这一行 | Fabric 新配置，抄自目录 | 实现只核长度和格式，不与目录行比（`catalog.go` 的 `accept`）。含义和权威见问题 8 |
| `intent.contract_ref` | `fabric-asset:{api_asset_id}` | Fabric 数据 | 实现要求非空、至多 160 个字符；契约说出站意图的 API 资产由它指明 |
| `intent.approval_ref` | `fabric-release:{release_id}/check-run:{check_run_id}`，98 个字符 | Fabric 数据 | 长度 4–128，网关据此记 `APPROVED`（推荐决策 6）。见第 5 条 |
| `intent.expected_generation` | Fabric 记下的这个目标的当前代次 | 只有网关知道，Fabric 跟踪 | 不等是 409，键不占用（推荐决策 3）。见第 6 条和问题 1 |
| `intent.route_priority` | 不写 | — | 可选 |

Fabric 不送、也送不了的：`route_id`、`path_match_mode`、`rewrite_path_prefix` 在网关目录里，RouteIntent 没有这些字段（网关 ADR-0020 背景末段）；`policy_version`、`desired_digest`、`observed_digest` 由网关产生。Fabric 不编译 agentgateway 配置（网关变更清单“V1.0 缺口整治后的必要接口契约变更”Fabric 一条）。

内容不变而 Release 换了，`release_ref` 和 `approval_ref` 也就换了。网关把它当作这条意图的新版本：整池重编、回读，旧记录变为 `SUPERSEDED`（网关 `tests/integration/fabric/README.md` 的 FB-03）。

### 5. `approval_ref` 指向 Fabric 的 Release 和它的检查

网关说“Fabric 批准”，而 Fabric 在 CR-0001 之后没有批准。两者这样对上：Fabric 的批准就是它的发布门禁。这个 Release 依据的检查在准备时满足现行策略，需要豁免的规则逐条写了理由（CR-0001 决定 1、2）；发布人在资产所属 Workspace 有 `internal_publisher` 角色（F05 §6.7）；目标、资产和 Release 都没有未解除的阻断。`approval_ref` 记这道门禁依据的检查，`release_ref` 记哪个 Release；谁、什么时候发布，在 Fabric 的操作记录和审计里，由 `idempotency_key` 里的操作编号找到。

这不是运行时授权。哪个工作负载能以哪个账户调用哪个操作，归 Gatekeeper（网关 G02 GW-INV-01、GW-INV-04；F02 §5.1 Policy & Review 不拥有运行时网关的最终授权）。

要网关接受的（问题 9）：

1. `approval_ref` 是引用，不是具名批准：没有批准人，也没有有效期。
2. 同一个人可以导入、检查、准备 Release 并发布（CR-0001 决定 3）。**这与网关的设计有出入。CR-0003 决定 4 的 Fabric 立场是沿用 CR-0001，需要网关负责人明确接受；不接受时另行决定。** 网关所有者 2026-11-19 取消的只是网关项目自身的角色分离和具名批准，原文写明“产品设计里的批准（API Fabric 批准路由意图……）是系统要实现的功能，不受它影响”（网关 `docs/governance/README.md`）。网关的实现只看 `approval_ref` 在不在、长度合不合格：状态机里的 `APPROVED` “只表示意图里已有长度合格的 `approval_ref`”（网关 ADR-0020 推荐决策 6），不核验它指向什么。
3. 策略更新后，旧 Release 仍会被发布或恢复（CR-0001 决定 5）。网关不能以“批准过期”拒收。
4. 网关不读 Fabric（网关 ADR-0006“现在”一节），也没有接口可查。可信的依据是 mTLS 的 Fabric 身份（推荐决策 2）；能放出什么路由由网关目录限定（推荐决策 4）。需要人工追溯时，用 Fabric 的 `getContractReleaseProvenance` 读出 Release 依据的修订、检查和豁免。网关 G03 §4 第 2 条要“复核调用主体权限、来源和签名/可信通道”，一期就是这个身份；是否另要签名，见问题 9。
5. 恢复旧 Release 时，送出旧 Release 的 `release_ref` 和 `approval_ref`、新的 `idempotency_key`。在网关那边这是一次新的发布，不是改写历史（网关 G03 §3：回滚“创建新受控事件”）。

凭证绑定自己也有必填的 `approval_ref`（网关 `credential-binding.schema.json`），那是网关或 Gatekeeper 的事，Fabric 不出。

### 6. 客户端：`fabric-worker` 用工作负载证书提交，一个目标同一时间一条

- **谁调用。** `fabric-worker`，不是 `fabric-api`：提交要重试、要等回读，属于持久任务（F02 §4.1）。`fabric-api` 只在槽位操作的事务里记下要提交什么。
- **身份。** 网关只认一个客户端 URI（`--fabric-identity`），取自证书 subjectAltName 里唯一的那个 URI；没有客户端证书握手就完不成，URI 不对是 401（网关 ADR-0020 推荐决策 2；网关 ADR-0021 背景）。所以所有 worker 副本用同一个身份。证书由签发网关信任的 CA 的一方提供，生产上是谁见问题 11。证书和私钥以文件挂给 worker：私钥 0600，只有 worker 读得到，不进数据库、日志和 `fabric-api`（F05 §4.1、§13）。服务端证书按部署配置里的 CA 和名字验证，不信任系统根。参照网关 ADR-0021（Proposed）的做法，每次新建连接重读证书文件，换证书不必重启 worker。
- **排队。** 槽位操作的事务里，路由表每一行写一条提交条目，与槽位、操作记录、审计和 Outbox 同事务提交。条目只记要提交什么（目标、路由行、Release）。正文在第一次送出时按当时的已知代次生成，连同规范摘要存下；之后的重试一律用存下的那份。worker 以租约和防护令牌领取条目（F03 INV-12）。一个网关路由目标同一时间只送一条，按操作的先后、再按路由表的行号：网关同一池上只能有一条未了结的发布，另一把键得 409 `publish_in_progress`（推荐决策 3），代次也只在 `ACTIVE` 时加一。同一槽位上的后一个操作取消前一个操作还没送出的条目，Fabric 记为“未提交即被取代”；已经送出的照常跟到底。
- **代次。** Fabric 为每个网关路由目标记一个已知代次，登记时为 0，标为“未核实”（问题 1）。一条意图到达 `ACTIVE`，已知代次加一；`REJECTED`、`FAILED` 不变。到 `UNKNOWN` 或 `PARTIAL` 时代次不确定：网关对账之后可能把它记成 `ACTIVE`，代次随之加一（网关 `internal/fabricpub/application/service.go` 的 `reconcileOne`）。这时这个目标暂停，等这一条有了结果再往下走。Fabric 不试探代次，因为试探的那一次就是真实提交。

网关的回答这样处理：

| 网关答 | Fabric 怎么做 |
|---|---|
| 202 | 记下 `intent_id`，开始读状态 |
| 409 `idempotency_key_reused` | Fabric 的缺陷（同键异体）。条目停住，告警 |
| 409 `publish_in_progress` | 池上有别的发布。退避后用同一把键、同一份正文重试 |
| 409 `generation_conflict` | Fabric 的已知代次不对。目标暂停，告警。核实代次之后，用同一把键按新代次重新生成正文（网关没有占用这把键） |
| 422 | 网关拒收这一条，原因如 `catalog`、`binding`、`schema`、`compile_refused`。条目记为“网关拒收”及原因，不重试，原样显示 |
| 401 | 身份配置不对。目标暂停，告警 |
| 400、404、405 | Fabric 的缺陷。条目停住，告警 |
| 503、500、超时、连接或握手失败 | 结果不确定。同一把键、同一份正文重试。网关先比幂等键、再比代次（`service.go` 的 `Submit`），所以第一次其实已被受理时，重试拿到的是第一次的 202 |

409 的原因词、422 的原因和 503 都不在契约里，是网关实现给的（网关 `internal/fabricpub/adapters/httpapi/handler.go`、`application/service.go`），见问题 5。

- **退避与超时。** 重试从 1 秒退避到 5 分钟，与 `fabric-worker` 的 Outbox 相同；不设放弃上限，第 12 次起告警并在槽位上显示，不像 Outbox 那样记为 `ABANDONED` 就停。POST 在 202 之前要编译并跑一次 `--validate-only`（推荐决策 5），拟用 60 秒；GET 拟用 10 秒。这两个数与网关回环套件的客户端相同（`run.py` 的 `fabric_request` 和 `wait_state`），不是网关承诺的上限（问题 12）。
- **网关不可达时。** 网关的控制面不在请求路径上（网关 ADR-0020 背景），已生效的路由照常服务（网关 G01 GW-FR-024）。Fabric 的队列积着，槽位显示最后一次读到的状态和读取时间（F02 §13.2）。

### 7. 状态回读：只抄网关的词，不造 `ACTIVE`

- 202 之后，worker 按 `intent_id` 读状态，间隔从 1 秒退避到 30 秒，直到 `ACTIVE`、`REJECTED`、`FAILED` 或 `SUPERSEDED`。`UNKNOWN`、`PARTIAL` 是网关交给对账的状态（推荐决策 6 的失败表），继续每分钟读一次，直到变化。每次读到的 HTTP 状态、`state`、`release_ref`、`desired_digest`、`observed_digest` 和读取时间都追加记下。
- 网关按 `intent_id` 只回最新一条没被取代的记录（`service.go` 的 `latest`）。所以 Fabric 每次都核对 `release_ref`：不是自己提交的那个 Release，说明这条意图之后又有提交，旧条目到此为止。新提交失败时，网关回的是新记录的 `FAILED`，池上跑的仍是上一条 `ACTIVE`；Fabric 靠自己记下的“这条意图上一次到达 `ACTIVE` 的 Release”知道池上实际是哪个（问题 4）。
- 每条路由的状态原样显示 16 个词之一，不翻译，也不用网关控制台的展示标签（网关 G03 §9）。Fabric 自己的提交进度用另一套词，不与网关的词混用：未提交、已提交、网关拒收、未提交即被取代。
- 槽位上另给一个汇总，也用 Fabric 的词：全部生效、进行中、需要处理。只有路由表每一行最新读到的都是 `ACTIVE`、`release_ref` 是槽位当前的 Release、两个摘要都非空且相等，才是“全部生效”。有任何一行是 `UNKNOWN`、`PARTIAL`、`FAILED`、`REJECTED`、网关拒收，或目标暂停，就是“需要处理”。
- 文档发布和路由生效分开显示。同一个外部提供方 API 在 `internal` 门户目标上 `ACTIVE`，只说明文档读得到；它的路由状态只来自网关路由目标。门户目标的 `delivery_status` 仍是 `UNKNOWN`，不受网关影响（F03 §8.3 的三种状态分开；网关变更清单 F07/F08；网关 G03 §0：“Fabric API Catalog 的文档可见性不自动转换为运行时 Route 可用性”）。

### 8. 撤回、回退和访问阻断

Fabric 能让网关做的只有一件事：在网关目录允许的范围内，提交某条路由的某个版本。

- **撤回（`WITHDRAW`）。** 网关一期没有撤回：`WITHDRAW_REQUESTED`、`REVOKING`、`REVOKED` 在词表里，但没有写出去的路径（推荐决策 6 末段）；目录行被一个 `intent_id` 占住后也放不掉（`catalog.go` 的 `Merge`）。所以在网关提供撤回之前，网关路由目标上的 `WITHDRAW` 拒绝（`GATEWAY_WITHDRAW_UNAVAILABLE`）；新 Release 少了路由表里的操作，或路由表要删一行，同样拒绝（`GATEWAY_ROUTE_REMOVAL_UNAVAILABLE`）。槽位不能显示“已撤回”而流量还在走。这与 FR-036 对门户目标的要求不同，CR-0003 里写明（问题 3）。
- **回退（`RESTORE`）。** 回到槽位上生效过的 Release，就是用那个 Release 把各条路由再提交一遍（第 5 条第 5 点）。某条路由在网关上最近一次 `ACTIVE` 的已经是这个 Release 的，这一条不再提交。
- **重提（新动作 `RESUBMIT`）。** 指针不变，槽位代次加一，对当前 Release 里还没到 `ACTIVE` 的行生成新条目、用新键。用于网关拒收之后改了目标配置或网关目录。现有的 `ACTIVATE` 对已生效的 Release 答 `RELEASE_ALREADY_ACTIVE`，做不了这件事。
- **网关操作员自己的回滚和发布。** `gateway-control rollback` 和手工 `publish` 绕过 `gateway-fabric`，它的状态目录看不见（网关 ADR-0020“成本与剩余风险”），Fabric 也看不见。Fabric 只显示网关回给它的状态，不推断（问题 15；漂移识别 FR-039 是 V1）。
- **访问阻断。** 阻断仍只管 Fabric 自己。被覆盖的 Release 在网关路由目标上不能激活、恢复或重提；还没送出的条目取消，已经送出的不追回。阻断不停止网关上的流量。网关上的紧急停止是撤销账户和按操作封禁，只由 `gateway-authz` 认的撤销者身份执行（网关 ADR-0012 推荐决策 4），不排在发布队列里（网关 ADR-0020 推荐决策 7）；Fabric 不持有这个身份，也不调用这些接口（问题 17）。门户在阻断旁写明这一点。网关路由目标上的阻断没有隐藏过任何内容，所以解除时不要求先撤回，不受 `WITHDRAW_BEFORE_CLEARING` 约束；解除仍须由另一位安全评审人执行（F04 §11.6）。

### 9. 失败模式

| 情形 | 结果 | 显示 |
|---|---|---|
| 一次激活的几条里有一条 422 | 其余照常提交；池上这一条仍是旧版本，或者没有 | 需要处理；那一行“网关拒收”及原因。改配置后 `RESUBMIT`，或 `RESTORE` 上一个 Release |
| 送出后网关不答或超时 | 同键同体重试 | 那一行“已提交”，带最后读取时间 |
| 到 `UNKNOWN` 或 `PARTIAL` | 目标暂停，等网关对账 | 网关的词原样；需要处理 |
| 409 `generation_conflict` | 目标暂停 | 需要处理；告警 |
| 证书过期、被换、CA 不对 | 握手失败，按结果不确定重试 | 告警；已生效的路由照常服务 |
| 网关改了目录 | 之后的提交可能 422 `catalog`：每次合并都对现有意图重新核对目录（`Merge` 调 `recheck`） | 拒收原因原样 |
| 网关操作员手工回滚或发布 | Fabric 看不到 | 仍是网关回给 Fabric 的状态（问题 15） |
| Fabric 数据库从备份恢复 | 已知代次可能回退；操作编号不重用，所以不会出现同键异体 | 恢复后所有网关路由目标标为“未核实”，暂停到核实为止 |
| 提交过程中建立了阻断 | 未送出的取消，已送出的跟到底 | 阻断和路由状态并列显示 |

## 备选与权衡

- **不对接，继续由 `gateway-control compile` 和 `publish` 发布。** Fabric 不用改。代价是网关 ADR-0006 的分工落空：网关的发布“批准还没有”（网关 `README.md`），网关阶段 0 的“新路由与认证方案声明走 API Fabric”要由网关所有者另定。
- **通用出站 Webhook。** 让 `fabric-worker` 把现有的槽位事件 POST 给网关，由网关自己组意图。Fabric 一侧最省事，但网关要的是带幂等键和代次的 `RoutePublicationIntent`，走 mTLS，还要回读状态（推荐决策 2、3）；现有的 Outbox 接收端用 Bearer、只收 Bento 信封、2xx 即算送达（`cmd/fabric-worker/README.md`），状态回不来，代次也排不了。组意图所需的目录数据仍在网关。不选。
- **Fabric 编译 agentgateway 原生配置。** 网关已经明确不要：“Fabric 不负责直接编译 agentgateway 原生配置”（网关变更清单）；编译、`--validate-only`、发布和回读都在网关（网关 ADR-0020 推荐决策 4、6）。Fabric 也会因此越过 F01 非目标 2。不选。
- **新增一种 `api_kind`（例如 `EGRESS_HTTP`）。** 把来源混进协议，按 `api_kind` 的过滤和概况都要改。不选，改用 `origin`。
- **复用门户目标，约定某个 `portal_key` 表示网关。** 少一张表。可是门户目标有受众配置、源站读取和 `delivery_status`，网关目标都没有；混在一起，读制品和解除阻断都要加例外，也容易把文档发布当成路由生效。不选。
- **另起一个上下文，自带 CAS 和历史。** 隔离更好，但要把 ADR-0004 已有的槽位、代次、操作历史和阻断重写一遍。不选；网关的事实只经稳定引用进入 Publication。
- **网关 `ACTIVE` 之后才切换指针。** 指针永远等于在跑的版本，看上去一致。可是 Fabric 的决定要等外部系统才能记下，失败时连决定本身都没有记录；网关 G02 §11.2 也要求 Fabric Release 与网关的期望、应用、观察各自独立，对账失败时“绝不自动显示 ACTIVE”。不选：指针记 Fabric 的决定，路由状态另记。
- **一个 Release 一次提交。** 契约是一条意图一条路由（网关 ADR-0020 推荐决策 4 的“为什么这样决定”），Fabric 做不到；中间状态的代价见问题 2。

## 影响

- **领域。** API Catalog：`APIAsset.origin`、`provider_id`。Publication：目标种类，网关路由目标的配置和路由表，提交条目，回读记录，每个目标的已知代次；槽位、操作和阻断沿用。Policy & Review：第 2 条的四条规则。统一语言新增“外部提供方 API”“网关路由目标”，届时补进 F03 §2。
- **管理 API（届时的下一个小版本）。** `AssetRegistration` 增加可选的 `origin`、`provider_id`，`APIAsset` 带回这两项。新增 `/v1/products/{product_id}/gateway-route-targets` 的登记、读取和路由表维护，以及其下的槽位读取（带每条路由的状态和汇总）与槽位操作。`PublicationAction` 增加 `RESUBMIT`，对把动作当作封闭集合的客户端属于 `RISKY`（F04 §5.1，与 0.20.0 增加角色相同）。新错误码 `ASSET_ORIGIN_MISMATCH`、`ROUTE_NOT_IN_RELEASE`、`GATEWAY_WITHDRAW_UNAVAILABLE`、`GATEWAY_ROUTE_REMOVAL_UNAVAILABLE`、`GATEWAY_TARGET_PAUSED`。现有 57 个操作的行为不变。
- **数据库。** `apicatalog` 加列，现有资产默认 `IDP_OWNED`。`publication` 增加目标种类，现有目标默认 `PORTAL`；增加网关目标的配置、路由表、提交条目（租约、尝试次数、最后的错误）、回读记录和已知代次。槽位和操作记录的约束要允许 `RESUBMIT`：代次加一、指针不变，操作记录带当前的 Release。回读记录只增不改，应用角色只授 `SELECT`、`INSERT`；其余授权随迁移给出。
- **安全。** worker 多一条出站 mTLS 连接，网络上只放行到部署配置里的网关端点（F05 §12 的出站限制）；私钥按第 6 条保管。授权矩阵加几行：登记网关路由目标和改路由表（产品负责人，同 AC-09），网关目标上的激活、恢复和重提（`internal_publisher`，同 AC-04），读路由状态（同槽位读取）。威胁登记册加一条：Fabric 或 worker 被攻破后，攻击者能在已配置的网关上启用目录里已有的路由或换它的版本，加不了上游和凭证，也撤销不了账户；网关目录是这条威胁的边界。CR-0001 取消的双人控制在路由发布上同样不存在，网关负责人的态度见问题 9。
- **门户（内部）。** 资产登记可选来源和提供方；外部提供方 API 带“外部提供方”标记；网关路由目标的登记页；槽位页逐条列出路由、网关的状态词、两个摘要和读取时间，汇总只用第 7 条的词；阻断旁写明不停流量，并指向网关的撤销和封禁。外部开发者门户不出现这些资产。
- **运维。** worker 的新配置：网关端点、服务端证书名和 CA、客户端证书和私钥的文件路径。告警：目标暂停、某条路由长时间不到终态、重试达到 12 次、证书临近到期。运行手册写明：要紧急停止流量，找网关的撤销和封禁，不靠 Fabric。

## 分阶段计划

- **P0 契约对齐与替身回环。** 先与网关负责人对齐下面的问题；这一步不写代码，CR-0003 决定之前也可以做。CR-0003 选择接下之后，实现第 1–8 条的最小集合：一个网关路由目标，`ACTIVATE`、`RESTORE`、`RESUBMIT`，回读。验证时 Fabric 的 worker 取代网关回环套件里的替身客户端，对着真实的 `gateway-fabric`、`gateway-authz` 和锁定的 agentgateway 1.7.0（网关 `tests/integration/fabric/README.md`）；套件能否让外部客户端驱动，见问题 16。退出条件：在 Fabric 一侧看到 FB-01、FB-02、FB-04、FB-05、FB-08 的对应结果，即全部生效时两个摘要相等、重放和两种 409、422 原样显示且网关没有变化、错误身份 401 之后目标暂停、`UNKNOWN` 不显示为生效；以及 Fabric 自己的：门户目标的 `ACTIVE` 不出现在路由状态里，同一目标上两个资产的提交串行、代次连续，阻断取消未送出的条目。同时在固定的网关提交上原样跑一遍网关自己的套件（两遍默认，加两个对照），作为基线。
- **P1 一家提供方，测试池。** 网关把 `gateway-fabric` 部署到一个真实的测试池（它一期不在 compose 和 systemd 里，网关 ADR-0020 推荐决策 1）；Fabric 的 INT 环境（F08 §9.1）用测试 CA 签的证书。提供方与网关负责人商定（问题 18）。退出条件：一个 Release 的全部路由“全部生效”；网关自己的流量用例通过；演练提交过程中网关重启、证书轮换、目录不一致的 422 和 `UNKNOWN` 对账；证据按 F08 §7 的模板记录，新的验收编号由 F08 责任人分配。
- **P2 生产前提。** 网关的阶段 2：PostgreSQL / Outbox、多副本和 Kubernetes（网关 ADR-0020 推荐决策 7；Kubernetes 上的 `gateway-fabric` 发布不在网关 ADR-0025 内，见其第 8 条）；撤回路径；读代次；生产 CA 和 Fabric 的工作负载身份；`PROD` 上游只用 TLS；漂移识别（FR-039）；F05 的安全评审、威胁登记和授权矩阵；F08 的生产准入（MS-09）。这些都满足之前不接生产池。

## 需与网关负责人对齐的问题

1. **当前代次怎么读**（`intent.expected_generation`；网关 ADR-0020 推荐决策 3）。代次一池一个，只在 `ACTIVE` 时加一，`UNKNOWN` 对账之后也可能加一；409 `generation_conflict` 的正文不带当前代次（网关 `internal/fabricpub/adapters/httpapi/handler.go`），契约里也没有读代次的路径。能否在 409 正文里给出当前代次，或加一个按 `target_id` 读代次和未了结发布的 GET？在那之前，Fabric 登记目标时的初始代次由谁、从哪里核实？
2. **一个 Release 有多条路由**（网关 ADR-0020“为什么这样决定”首段；推荐决策 3 的 `publish_in_progress`）。一个外部提供方 API 通常有几条路由（万邦、顺丰的目录各四条），一次激活就是几次整池重编和发布，中间池上新旧版本混着。网关是否考虑把同一 `release_ref` 的几条意图作为一次池发布提交？或者提供只校验、不发布的预检，让 Fabric 在记下决定之前知道每一条会不会 422？
3. **撤回一条路由**（`ReleaseState` 的 `WITHDRAW_REQUESTED`、`REVOKING`、`REVOKED`；推荐决策 6 末段；`catalog.go` 的 `Merge`）。何时、用什么请求撤回一条路由并释放目录行？在那之前 Fabric 拒绝网关目标上的撤回和删路由（第 8 条），网关是否接受？
4. **按发布查状态**（`GET /v1/route-intents/{intent_id}/status`；`service.go` 的 `latest`）。状态只回这个 `intent_id` 最新一条没被取代的记录，新提交失败时读不到池上实际 `ACTIVE` 的那一条。能否按 `idempotency_key` 或 `(intent_id, release_ref)` 读，或在状态里带上当前 `ACTIVE` 的 `release_ref`？
5. **错误正文和原因词写进契约**（契约的 409、422 没有正文模式）。实现回 `{"error", "reason"}`，原因有 `idempotency_key_reused`、`publish_in_progress`、`generation_conflict`、`catalog`、`binding`、`schema`、`sensitive_key`、`compile_refused`、`body_too_large` 等，另有 400、401、404、405、503（网关 `internal/fabricpub/` 下的 `adapters/httpapi/handler.go`、`application/service.go` 和 `domain/`）。请写进契约并保持稳定，Fabric 按原因词分支（第 6 条的表）。
6. **契约与实现以哪份为准**（网关 `contracts/gateway/route-intent.schema.json`、`contracts/fabric/route-publication-intent.openapi.yaml` 与 `envelope.go` 的 `parseIntent`）。`upstream_tls` 在模式里只有 `VERIFY_REQUIRED`，实现在非 `PROD` 另接受 `PLAIN_HTTP_SANDBOX_EXCEPTION`，万邦的目录和回环套件都在用；`contract_ref`、`policy_bundle_ref`、`transport` 在模式里可选，实现必填；`allowed_methods` 模式允许多个，实现只许一个；实现另要求 `gateway_pool` 以 `(ingress|egress|ai)-(dev|test|prod)` 开头并与流量类、环境一致；202 的描述写“Validation has not happened yet”，推荐决策 5 却在 202 之前校验。契约（`info.version` 1.0.0，标题带 DRAFT）会不会改，怎样升版？
7. **目录数据从哪里来**（推荐决策 4 的 `--pool-base`；“成本与剩余风险”：“新操作要先改只读的 `--pool-base`”）。`intent_id`、`logical_path`、上游四项、`credential_binding_ref`、`authz_profile`、`policy_bundle_ref` 都要与 pool-base 一致，Fabric 只能手抄。能否以同一个 mTLS 身份提供只读的目录读取？`intent_id` 以目录行里的为准，还是由 Fabric 起？目录加了操作，怎样让 Fabric 知道？
8. **`authz_profile` 和 `policy_bundle_ref` 的含义**（网关 G03 §1：`AuthzProfile` 归 Gatekeeper PDP，`PolicyBundle` 归 Gateway Publisher；`catalog.go` 的 `accept` 不与目录行比）。Fabric 应送目录行里的值，还是这两项改由网关从目录填？
9. **接受第 5 条的 `approval_ref`**（推荐决策 6 的 `APPROVED`；网关 G03 §4 第 2 条；网关 G03 §9“高风险操作需具名审批、职责分离”）。值是 Fabric Release 和检查的引用，没有具名批准人和有效期，同一个人可以从导入做到发布。网关是否接受？一期“复核调用主体”是否就是 mTLS 身份，是否还要签名？
10. **`target_id` 和端点**（信封的 `target_id`；推荐决策 4 的 `--target-id`；契约的 `servers.url` 是草案名，网关 ADR-0020 背景）。Fabric 拟一个 `gateway-fabric` 进程对应一个网关路由目标，`target_id` 由 Fabric 定、网关照填。端点地址和服务端证书名由谁给？阶段 2 一个池上有多家提供方时，这个对应会不会变？
11. **Fabric 的工作负载身份**（推荐决策 2 的 `--fabric-identity`；网关 ADR-0021，Proposed）。生产上由谁签 Fabric 的客户端证书，信任域和 URI 是什么（套件用 `spiffe://idp.test/fabric/publisher`），有效期和轮换周期多长？不查 CRL 和 OCSP，证书泄露时怎样停：换 CA，还是改 `--fabric-identity`？
12. **时延上限**（推荐决策 5：“若 POST 的时延不能接受”）。POST 在 202 之前编译并跑 `--validate-only`，网关没写 POST 和从 202 到终态的上限。Fabric 拟 POST 60 秒、GET 10 秒（与套件相同），请确认或给值。
13. **环境与池**（`intent.environment`；池名规则）。Fabric 只有 `sandbox`、`production`，网关有 `DEV`、`TEST`、`PROD`。一期接 Fabric 的是否只有 `egress-test`？`DEV` 池接不接？
14. **认证方案的声明与核对**（网关 ADR-0020 抬头“认证方案声明走 API Fabric”；背景末段“RouteIntent 上没有 `auth_scheme`”；推荐决策 5；`credential-binding.schema.json`；网关 `docs/production-release-plan.html` 轨道 B 的 B1）。B1 列的 Tier 1 有 HTTP Basic，Tier 2 有 `WANB_DEVELOPER_TOKEN`、`SF_INTL_ENVELOPE`，绑定模式的 `auth_scheme` 没有这些。Fabric 的 `x-idp-provider-auth` 用哪套词？网关是否要 Fabric 的声明参与核对（意图里带上，或按 `credential_binding_ref` 回答方案）？新增或修改一个绑定（`--bindings` 文件）由谁、走什么流程？
15. **绕过 `gateway-fabric` 的发布和回滚**（网关 ADR-0020“成本与剩余风险”）。一期是否承诺对接了 Fabric 的池只有 `gateway-fabric` 一个写入方？操作员用了 `gateway-control rollback` 或 `publish` 之后，Fabric 从哪里知道？
16. **回环套件的外部客户端**（网关 `tests/integration/fabric/run.py`，Fabric 一侧是替身客户端）。能否加一个只起服务、导出证书和端口、由外部客户端驱动的模式，供 P0 使用？
17. **阻断与封禁的关系**（网关 ADR-0012 推荐决策 4；网关 ADR-0020 推荐决策 7；网关 G03 §4 第 7 条）。Fabric 不持有撤销者身份，不调用撤销和封禁。网关是否希望收到 Fabric 的 `access_block.created` 事件作为提示？要的话经什么通道？
18. **P1 用哪家、哪个池**（万邦的明文沙箱例外，见问题 6；顺丰的内部签名器，`catalog.go` 的 `upstreamHost`）。用哪一家提供方、哪个池、固定哪个网关提交？
19. **阶段 2 的语义**（网关 ADR-0020“变更与回退条件”末段：HTTP 正文、16 个词、代次和“回读摘要相等才是 `ACTIVE`”不变）。多副本之后代次是否仍是一池一个计数？`PARTIAL` 是否开始表示部分副本成功（一期只表示策略文件和快照落在不同代次，推荐决策 6）？
20. **入口流量**（网关 ADR-0020“要仓库所有者定的”第 4 项；RouteIntent 的 `INGRESS` 分支要 `api_asset_ref`）。Fabric 自有 API 经入口网关发布，是否在网关的计划里？在的话另写一篇 ADR，不放进本篇。
