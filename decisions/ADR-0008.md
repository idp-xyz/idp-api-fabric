# ADR-0008 — 检查之外执行的 10 条规则如何计入检查结论

- **状态**：Proposed（未具名批准）
- **文档基线**：V1.0，不独立升级版本
- **关联**：F04 §7.1、§8、§11.4、§11.5、§11.6；`governance/policies/F04_Rules_Registry.json`；`internal/policyreview/domain/baseline.go`、`checkrun.go`；`internal/policyreview/application/approval.go`。
- **决定人**：Governance Owner（待具名）。F04-GOV-015、017、019、025、026 的负责角色是 SecurityOwner，需要参与。

> **CR-0001 之后（2026-11-26）**：[CR-0001](CR-0001.md) 取消了评审，不再有评审人读检查结论。准备 Release 只看逐条规则的结果，`outsideContractChecks` 不因这 10 条是 `NOT_RUN` 而拒绝，现在位于 `internal/policyreview/domain/release.go`（`application/approval.go` 已删除）。开发侧建议不再推进本 ADR；是否关闭由 Governance Owner 决定。下文“影响”一节所说的重新评审、批准和 `approval_problem`，在管理 API 0.37.0 中已不存在：策略更新后，已有 Release 照常发布和恢复，只有准备新 Release 时才要求现行策略下的检查。

## 问题
检查的基线是登记表里阶段为 MVP 的 23 条规则。其中 F04-GOV-014–020、025–027 这 10 条管的是 Release、发布、评审和渲染，检查一个草稿修订时这些还不存在，检查里没有工具评估它们，每次都记为 `NOT_RUN`。

一次检查的 `status` 在没有 `FAIL` 时，只要有一条规则是 `UNKNOWN` 或 `NOT_RUN` 就是 `UNKNOWN`（`checkrun.go` 的 `Summary.Status`）。所以目前检查结论只会是 `FAIL` 或 `UNKNOWN`，永远不会是 `PASS`。评审人从结论上分不出“有判断不了的风险”和“文档规则都通过了”。

这 10 条并不是没有执行：6 条在导入、评审、准备 Release、发布或渲染时执行，F04-GOV-018 由检查记录本身满足，019 和 026 暂不适用，027 靠如实报告 `UNKNOWN`（F04 §11.4 的对照表，随 PR #68 加入）。准备 Release 和发布时，`outsideContractChecks` 已经不因这 10 条是 `NOT_RUN` 而拒绝。但登记表仍把它们记为 `F07_TOOL_ADAPTER` 或 `MANUAL_REVIEW`，检查结论也照旧把它们计入。

## 候选决策
**方案 C（建议）：保留在检查里，但不计入结论。**
1. 登记表为这 10 条改用一个新的 `verification_mode`（例如 `OUTSIDE_CHECK`），并写明在哪一步执行。
2. 检查仍列出全部 23 条 MVP 规则，这 10 条仍记 `NOT_RUN`；汇总 `status` 时不计入它们。
3. 规则结论增加一个标记，说明这条规则在检查之外执行（管理 API 升一个小版本）。
4. `outsideContractChecks` 的名单改为由登记表的 `verification_mode` 决定，不再在代码里另列一份。

理由：`baseline.go` 的注释写明了设计原意，即“读检查的人要先知道哪些规则没有跑”。方案 C 保留这一点：评审人在检查里仍看得到这 10 条，也看得到它们在哪里执行。

## 备选与权衡
- **方案 A：移出检查。** 检查只列 13 条，结论可以是 `PASS`，契约没有新字段。代价是评审人在检查里看不到这 10 条，只能查文档，与 `baseline.go` 的设计原意相反。
- **维持现状。** 不改代码。检查结论永远不是 `PASS`，评审人继续靠文档区分 `UNKNOWN` 的来由。
- **与 F04 §8 的关系。** F04 §8 要求“单个 PASS 不得传播成整个流水线 PASS”，`checkrun.go` 据此规定 `PASS` 是“每条规则都评估过且没有发现”。方案 A 和 C 都把“每条规则”收窄为“检查负责的规则”。所以采纳之后，检查的 `PASS` 只说明文档规则通过，不能读作 Release、发布或渲染也已通过；这一点要写进 F04 §8 和 §11.4。
- **两个方案的工作量相近。** 都要改登记表、与登记表的对齐测试（`policy_test.go`）、数十处断言 `UNKNOWN` 的测试，并同步 F03、F04、F05 和 README。

## 影响
新策略的 `policy_digest` 与旧的不同，旧检查不再“现行”：
- 已批准、还没做成 Release 的修订：准备 Release 返回 409 `POLICY_STALE`，要在新策略下重新检查、重新评审。
- 已做成 Release、还要在新目标上 `ACTIVATE` 的：同样需要新的批准。
- 已在槽位生效的：照常提供读取，`WITHDRAW` 和内部目标的 `RESTORE` 不受影响（合作方目标的恢复要求当前批准）；但槽位的 `approval_problem` 会显示 `POLICY_STALE`，直到重新评审。

统计受影响批准的只读查询。它已在本地迁移过的测试库上用 `EXPLAIN` 验证过表名和列名，没有在生产库上运行过：

```sql
SELECT r.product_id, r.api_asset_id, r.revision_id, r.review_id, c.valid_until,
       EXISTS (SELECT 1 FROM contractregistry.contract_release cr
               WHERE cr.review_id = r.review_id) AS released,
       EXISTS (SELECT 1 FROM contractregistry.contract_release cr
               JOIN publication.slot s ON s.active_release_id = cr.release_id
               WHERE cr.review_id = r.review_id) AS active_somewhere
FROM policyreview.review_request r
JOIN policyreview.review_conclusion c ON c.review_id = r.review_id
WHERE c.outcome = 'APPROVED' AND c.valid_until > now()
ORDER BY r.product_id, r.api_asset_id, c.valid_until;
```

`released` 为假的要重新检查和评审；`active_somewhere` 为真的，其槽位会出现 `approval_problem`。

## 需验证及批准
1. 具名 Governance Owner 选定方案 C、方案 A 或维持现状，并确认检查 `PASS` 的含义收窄（见“与 F04 §8 的关系”）。
2. SecurityOwner 确认 F04-GOV-015、017、019、025、026 的执行位置成立。其中 015 的例外（按编号下载不看访问阻断，F05 §6.9）另行裁决，已由 [CR-0002](CR-0002.md) 裁决：0.38.0 起按编号下载看这个 Release 在任一目标上的阻断。
3. 在生产库运行上面的查询，按受影响批准的数量确定上线时机。
4. 选定后另开实现 PR，引用本 ADR 和决定记录。登记表里 F04-GOV-011、012、013 的 `verification_mode` 与实现不一致（F04 §11.4），可以一并裁决。
